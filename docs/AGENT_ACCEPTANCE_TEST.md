# Lookout agent acceptance test — v0.3.0

Use a test repository with an observed GitHub snapshot in Lookout. Do not use live customer secrets. Use two distinct **repository-scoped** tokens from **Connect your coding assistant** on the same repository detail screen. Keep both credentials private.

## Before starting
1. Check the Lookout production deployment is READY and the production schema contains `agent_contributions`.
2. Verify the package is actually on npm: `npm view @good-ship/lookout-mcp@0.3.0 version`. If it returns a 404, publishing has not completed. Do not use a floating npm version as a substitute.
3. Open the dashboard, the **Agent activity** page, and your test project. Keep the dashboard open for read-back.
4. Create token A for Codex and token B for Claude Code, independently. Configure the connection using the setup commands generated by Lookout. Both point to `https://lookout-eosin.vercel.app` and run `npx -y @good-ship/lookout-mcp@0.3.0`. Never paste actual tokens into chats, git files or CI logs.

## Agent A: report a handover
In Codex, request:

> Call lookout_get_handover. Tell me what evidence you can independently observe and what is unverified. Then call lookout_submit_contribution with kind=handover and the following version-1 checkpoint (this is a deliberately fictional acceptance report, not a real completed feature).

Example input for `lookout_submit_contribution`:

```json
{
  "kind": "handover",
  "checkpoint": {
    "version": 1,
    "eventId": "lookout-acceptance-20261023-a-01",
    "agent": "Codex acceptance test",
    "title": "Acceptance handover — synthetic task",
    "objective": "Validate scoped contribution handover",
    "summary": "No code changes made. Demonstrating how a handover is retained.",
    "implemented": [],
    "remaining": ["Agent B should retrieve this exact event ID"],
    "tests": [{"description": "Cross-agent read-back", "result": "not_run"}],
    "decisions": [],
    "blockers": []
  }
}
```

Expected: a successful append response with an attributed, **unverified** entry on the project's timeline. Do not mark the work human-confirmed.

## Agent B: pick up the work
In Claude Code, request:

> Call lookout_get_handover and lookout_get_contributions. Find event `lookout-acceptance-20261023-a-01`, report its proposed next action, and clearly label it agent-reported. Submit your own progress contribution with a *different* eventId. Do not claim a test passed unless you ran it.

Expected: Agent B reads Agent A's report without copying transcripts. A new entry appears in the same logical project. Each entry retains its agent and token attribution.

## Permissions and failure cases
1. **Idempotency:** submit Agent A's original exact request again. It should return a duplicate acknowledgement, not a second row.
2. **Conflict:** change the summary while keeping the same event ID. Expected HTTP 409 conflict.
3. **Isolation:** create a token for a *different repository*. Its `lookout_get_contributions` must not reveal repository A's contributions, even if both repositories map to one logical project. Its writes must remain tied to the repository from its token.
4. **Revocation:** revoke token A from Lookout's project connections. A further contribution using token A must fail with HTTP 401 or 403; B remains functional.
5. **Contradiction:** submit an agent claim that CI passed when observed GitHub evidence shows a failure. The UI must not elevate the claim to verified CI or human-accepted status.
6. **Limits:** avoid intentionally posting 100+ events to production. Confirm rate-limit coverage in automated tests instead.

## CLI fallback
If you want to verify REST submission independently of a coding assistant, save the checkpoint object above (the inner `checkpoint` only) to `checkpoint.json`. Set `LOOKOUT_API_URL` and `LOOKOUT_API_TOKEN` as private environment variables and run:

```bash
npx -y -p @good-ship/lookout-mcp@0.3.0 lookout-report ./checkpoint.json --kind handover
```

Use a **new event ID** for each independent test; reuse one only to test idempotency.

## UI release checks
- Overview: actionable projects and agent reports appear in separate panels with clear provenance.
- `/agents`: reports sorted newest-first, with agent, project, repository, proposed next step and explicit unverified labels.
- Portfolio project: an agent contribution has a detailed evidence panel and can be traced to the right repository.
- `/demo`: public fictional workspace remains unauthenticated, while `/`, `/agents`, `/portfolio` and other real-account routes remain protected.
- Test desktop and phone widths, keyboard focus and empty-state behaviour.

## Pass criteria
Both agents can independently connect, A writes, B reads and writes, duplicate replay is safe, conflict/isolation/revocation behave correctly, GitHub evidence stays independent of agent claims, and authenticated/live data never appear in the public demo. Record actual evidence and failures before marking acceptance complete.
